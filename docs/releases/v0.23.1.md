# plumb v0.23.1 - cloud setup: where CLAUDE_CODE_SUBAGENT_MODEL has to be set

`docs/cloud-setup.md` (0.23.0) said a setup script could put `CLAUDE_CODE_SUBAGENT_MODEL` in the `env`
object of `~/.claude/settings.json`. It cannot.

## What changed for users

- The "Route the subagents" section now says to set the variable as a real environment variable of the
  session, in the environment's own settings, and the `settings.json` snippet is gone.
- No code changed. The hook for `role.explorer.model` is not affected: it reads plumb's config, not
  the environment.

## Do you need to do anything

If you followed 0.23.0 and wrote the variable into `settings.json`, it has no effect: move it to the
environment's variables. `plumb-doctor` tells you which case you are in: under "routing targets" it
prints `CLAUDE_CODE_SUBAGENT_MODEL: unset` while the variable is not in the session's environment.

## Verification

Measured in a cloud session on Claude Code 2.1.322, headless (`claude -p`, models read from
`modelUsage`, the shell's environment read through a Bash call):

- With the variable only in the user `settings.json` `env`, a general-purpose subagent ran on the main
  session's model, and the shell did not have the variable. Another name in the same object did reach
  the shell.
- With the variable only in a `--settings` `env`, the same: the subagent was not changed and the shell
  did not have it, while a second name in that object did reach the shell.
- With the variable in the process environment, the subagent ran on the variable's model.

`bash scripts/check-harness.sh` passes.
