# plumb v0.13.0 — an implementer you can watch

The implementer role used to be a subagent on the main session's model. It can now run as its own
agent in a visible pane, on whatever model tier you point it at, while the main session keeps the
judgment.

## What changed for users

- **`role.implementer = <command>`** starts the implementer through `pane.driver` in a new pane,
  hands it a brief file, and waits on its agent state. Every playbook that hands work to the
  implementer role uses it, and so do `plumb:lead` lanes.
- **`role.implementer.model = <model>`** sets the model of the subagent fallback, used when the key
  above or a usable pane driver is missing.
- **The split is written down.** Requirements, design, ambiguous implementation, verification and
  final integration stay in the main session; the implementer gets implementation whose range and
  acceptance are fixed. A report without check output is not done, and an unclear brief comes back
  instead of being decided in the pane.

The model names live only in your config. When a new model generation changes which tier fits
which work, change the config line; the role split stays.

## Compatibility

Both keys are optional. Unset, the implementer is a `Task` on the main session's model, as before.
`plumb:lead` still uses `role.bulk` for lanes when `role.implementer` is unset. Codex does not read
either key; implementer work there goes to `plumb_worker`.
