# plumb v0.22.0 - ledger: records for a warehouse

`views` writes the tables plumb defines. To query the requests themselves in a warehouse, they had to
be read out of each session branch of the store by hand, and priced again outside plumb.

## What changed for users

- `plumb-ledger records --since <day> --until <day> [--out <file>]` prints the period's requests as
  JSON lines: the allowlisted fields, then `cost_usd` (list price, exact, `null` when unknown),
  `price_version` and `conflict`. It reads the same sources as `report`. The same records give the
  same bytes, so a scheduled load can merge on `id` and re-run safely.
- A store that is set but cannot be read is an error and nothing is written, so a load never takes a
  partial read for the whole.
- `assets/bigquery/requests.schema.json` is the table's schema, and `docs/ledger.md` shows a staging
  load and a `MERGE` for BigQuery. plumb does not install that job.

## Verification

`scripts/test-ledger-views.py` checks the fields and their order against the schema file, the exact
cost and `null` for an unpriced model, the period filter, byte-identical reruns with `--out`, that the
ledger directory is unchanged, the conflict flag, reading a store-only record, and the error with
nothing written for an unreadable store. The BigQuery commands in the docs were not run against
BigQuery.
