# 文章の規則（日本語）

エージェントが人に向けて日本語で書く文章（報告、PR 本文、コミットメッセージ、文書）の規則。生成された文章を読みにくく、信用しにくくする癖を一つずつ挙げ、代わりに何を書くかを決める。英語の文章は [`writing.md`](writing.md) に従う。番号はそれぞれ別に振る。

規則の番号（J1 など）は固定で、レビューや他のファイルから引用できる。やめた規則も番号と行を残し、やめたことを書く。引用が別の規則を指すことはない。

今書く文章、書き直す文章に当てはめる。既存のファイルをこの規則のためだけに書き直さない。コードのコメントはここでは扱わない。コメントの量はリポジトリの契約の `[code_policy]` で制限する（`docs/project-contract.md`）。

## 中身

- **J1. 仕組みを書く。** 今回の作業について書くときは、コマンド、ファイル、数字、誰が何をしたかを書く。作業についての記述が別のプロジェクトの文書にそのまま載せても通じるなら、何も伝えていないので、書き換えるか消す。この文書の規則のような一般的な決まりは、作業についての記述ではない。
- **J2. 強調語の代わりに数字を書く。**「大幅に速くなった」ではなく「4.2 秒から 0.9 秒になった」。「たまに落ちる」ではなく「40 回中 3 回落ちる」。
- **J3. 出典は名前で書くか、書かない。**「一般に〜と言われている」ではなく「上流の README には〜とある」。
- **J4. ぼかしは一つの主張に一つまで。**「〜かもしれない可能性があります」のように重ねない。確かさは、ルーター（`SKILL.md`）が求めるラベル（measured・inferred・guessed）で示す。
- **J5. 最後の事実か次の行動で終える。** 本文を言い直すまとめの段落や「以上のように〜は有効な手段と言えるでしょう」を書かない。

## 言葉

- **J6. 開発用語は訳さずそのまま書く。** merge、worktree、cache、idempotency key はそのまま使う。独自の和訳語（「併合」「作業木」）や比喩的な言い換えを作らない。読み手が普段使う言葉で書く。
- **J7. 同じものは同じ名前で呼ぶ。** 一度決めた呼び方を繰り返す。言い換えて変化を付けると、別のものを指しているのかと読み手が迷う。
- **J8. 中身の無い飾りの言葉を使わない。**「包括的な」「シームレスな」「堅牢な」「革新的な」「多岐にわたる」「さまざまな」「〜を実現」「〜を推進」。何がどうなるかを書く。
- **J9. ビジネスのカタカナ語より普通の言葉を使う。**「レバレッジする」ではなく「使う」、「アジェンダ」ではなく「議題」、「インサイト」ではなく「分かったこと」。J6 の開発用語はこの対象ではない。
- **J10. 比喩より字義どおりの言葉を使う。**「北極星」「羅針盤」「エコシステム」「土台を築く」のような言い方をしない。コードを人のように書かない（「パーサーがトークンを欲しがる」）。
- **J11. 冗長な表現を削る。**「〜することが重要です」「〜という点に注意が必要です」「〜という形で」「〜させていただきます」は、消すか短い言い方にする。

## 文

- **J12. 一文に一つのこと。** 読み返さないと分からない文は分ける。読点で三つ以上の節をつないだ文は分ける。
- **J13. 主語を書く。**「〜が行われた」「〜とされる」より「CI が〜を実行した」と書く。動作主が分からないか、どうでもよいときだけ受け身にする。
- **J14. 事実を足さない添え句を付けない。**「〜することで、信頼性の向上につながります」の後半のような句は削る。事実が入っているなら独立した文にする。
- **J15. 対比で飾らない。**「A だけでなく B も」「〜ではなく、〜なのです」の形にせず、言いたいことをそのまま書く。
- **J16. 何でも三つに揃えない。** あるだけ挙げる。二つなら二つ、四つなら四つ。
- **J17. 言い切るか、確かさのラベルを付ける。**「〜と言えるでしょう」「〜ではないでしょうか」で結ばない。
- **J18. 言い直さない。**「つまり」「要するに」で同じ内容を繰り返さない。一度で伝わる書き方を一度書く。

## 形

- **J19. 箇条書きの項目も文で書く。**「〜の改善」「〜の対応」のような名詞止めだけを並べず、何をどうしたかを書く。
- **J20. 太字は判断に効く所だけ。** 用語ごとに太字にしない。「**性能：** 性能が改善した」のように行の中身を繰り返す見出し語を付けない。
- **J21. 絵文字と感嘆符を使わない。** 見出しに記号の飾りを付けない。
- **J22. 会話の前置きと締めを書かない。**「ご質問ありがとうございます」「〜について説明します」「お役に立てれば幸いです」「何かあればお知らせください」を書かず、答えから始める。
- **J23. 括弧の補足は一文に一つまで。** ダッシュ（——）で挿入をしない。補足が長くなるなら文を分ける。

## 文書

- **J24. 一つの文書に一つの型。** 手を動かして学ぶ入門、一つの目的に着く手順、引くための参照、理由を述べる解説を一つの文書に混ぜない。混ざったら分けて互いにリンクする。
- **J25. 条件と注意は手順の前に書く。**「base が赤なら止めて報告する」と書き、「止めて報告する（base が赤の場合）」と後ろに回さない。
- **J26. 順序のあるものは番号付きで、それ以外は箇条書きで。** 番号の一つに指示は一つ、命令の形で書く。
- **J27. 数や構成の主張は、それを入れる commit の時点で正しくする。** 出し直すコマンドを添え、読む人が信じる代わりに確かめられるようにする。

## 確かめ方

送る前に、上の節ごとに一度ずつ読み直す。レビューで違反を見つけたら番号で指摘する。コマンドで確かめられる規則が出てきたら、そのコマンドに移し、ここの行はそのコマンドを指すように書き換える（`principle-encode-lessons-in-structure`）。
