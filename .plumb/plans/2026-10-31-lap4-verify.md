# Lap 4 — verification (spec §F)

**spec**: `.plumb/specs/project-contract-and-improvement-loop.md` §F, acceptance F and the lap-4 clause of
G. This plan is disposable; where it and the spec disagree, the spec wins.

## Why now

A cloud session asked "「動作確認して」と言われたらどう動く？" answered with generic steps: nothing in
plumb is reached by that request, and SAKUJI's verifier (skill `feature-verify`, agent `verifier`,
comparator `compare.mjs`, Feature Map) lives in SAKUJI draft #1675 under `docs/agents/`, which Claude
Code does not load. Lap 4 gives the request a skill in one hop and moves the parts that are not
product-specific (protocol, comparator, the verifier's role) into plumb. SAKUJI is the first consumer.

## Decisions

| # | Decision | Why | Rejected |
|---|---|---|---|
| 1 | The observation row and threshold rules are SAKUJI's `verify-metrics/1` and `thresholds.json` shapes, documented as plumb's protocol, plus an explicit `status` | The first consumer already produces them with tests; SAKUJI changes only its contract | A new row shape (SAKUJI rewrites its measurer for nothing) |
| 2 | Rows without `status` derive it: `ok: true` → `ok`; `error` starting `harness:` → `harness_error`; other `ok: false` → `scenario_failed` | Keeps SAKUJI's runs (and past `runs/`) readable | Rejecting legacy rows |
| 3 | Comparator is Python (`scripts/verify_compare.py`, `plumb-verify compare`), a faithful port of `compare.mjs` | plumb's tools are Python/bash; Node is not a plumb dependency | Shipping the .mjs |
| 4 | Thresholds come from the contract: new key `[verify] thresholds` (path, repo-relative) | Spec: "thresholds from the contract"; without a key the comparator cannot find them | A plumb default threshold set (one product's numbers would become everyone's) |
| 5 | `plumb-verify plan` reports the contract with one outcome and exit (see Preflight) | The skill's step 0 and acceptance G need one deterministic check | Letting the skill read TOML itself |
| 6 | `plumb:verify` is a new skill whose description is reached by 「動作確認して」 and its neighbours, measured with trigger cases before release | The lap-1 lesson (open-pr): a rule a request must reach is measured by routing | Adding a row to the root skill only |
| 7 | `agents/verifier.md` is plumb's canonical verifier (no pinned model, rule 12); the project's procedure is the file named by `verify.scenarios` | Spec §F; the role and prohibitions are generic, the steps are the product's | Copying SAKUJI's steps into plumb |
| 8 | Without a `[verify]` contract the skill says so and runs the repository's own tests as tests, never calling it verification | An honest fallback; no repository is forced to adopt the protocol | Refusing to act |
| 9 | **The base revision's contract is the trusted one.** `plumb-verify plan --base <sha>` reads `.plumb/project.toml` from the base commit (`git show`), and every project command and the thresholds come from a worktree of the base. A contract or procedure changed by the head is reported as a change under test, never used | A head could otherwise rewrite `verify.up`, the procedure or the thresholds it is judged by | Trusting the current worktree's contract |
| 10 | **The head runs code, so it must be one the owner already trusts**: `plan` refuses a head that is not contained in a branch of `origin` (a fork's `refs/pull/N/head` is not), unless `--allow-untrusted-head` is given by the owner; the skill never runs in CI with secrets (`pull_request_target`) and only in a disposable environment without production credentials | Starting the candidate executes its build scripts and dependencies | Assuming the launcher isolates it |
| 11 | **Completeness needs the selection, not only the rows**: `compare` requires `--expect <manifest>` (the selection the run committed to: expected `feature/scenario/role` keys, unmapped paths, scenarios not run with their reason). An expected key with no row on either side, an expected screenshot (`shots: {key: [names]}` in the manifest) with no shot-diff row, an unmapped path, or a not-run scenario makes the result `incomplete` | Rows alone cannot show what was never measured | Inferring scope from the rows |

## Interfaces (docs/verify-protocol.md)

- **Observation row** (JSON Lines, one per scenario × role × side × run): `feature`, `scenario`, `role`
  (the key is `feature/scenario/role`), `side` (`base` | `pr`), `status` (`ok`,
  `start_failed`, `scenario_failed`, `harness_error`, `not_run`), `repeat`, metric fields (numbers,
  lists such as `"404 GET /x"`, maps such as `pageerrors_known`, `growth_per_iter.{field}`),
  optional `restore_check {ok,…}`, `cleanup_error`, `artifacts` (paths, never committed blobs).
  The last row per key and side wins.
- **Thresholds file**: `version`, `status` (e.g. provisional), `min_repeat_for_growth`, `metrics`:
  `{name: {rule, …}}` with rules `increase_abs {max, field?}`, `known_diff {min_abs, max_ratio}`,
  `list_new {max}`, `increase_ratio_and_abs {min_abs, max_ratio}`, `growth_diff {max}`, `abs_max
  {max}` (screenshot diffs only). An unknown rule is an error (exit 2), never skipped.
- **Shot-diff rows**: `{key, name, ratio}` or `{key, name, missing: "base"|"pr"}`.
- **Comparator** `plumb-verify compare --base <rows> --pr <rows> --thresholds <file> --expect
  <manifest> [--shot-diffs <rows>] [--out <file>]`. Output `plumb-compare/1`: `result`, `summary`,
  `thresholds {version,status}`, `compared`, `regressions [{key, metric, base, pr, delta,
  threshold}]`, `notes [{key, kind, detail}]`, `missing {…}`. Exit: `no_diff` 0, `regressed` 1,
  `incomplete` 3, usage or malformed input (bad JSON with its line number, unknown rule, a
  non-object row) 2. **There is no pass.** Precedence: any regression → `regressed` (the missing
  scope is still listed); else any incomplete cause → `incomplete`; else `no_diff`.
- **Incomplete causes** (spec §F): an expected key with no row on either side; a key on one side
  only; `start_failed`, `not_run`, `harness_error` or `scenario_failed` on **either** side (a
  candidate-only scenario failure is `incomplete` with note `pr_failed`, as the spec says, not a
  regression); `cleanup_error`; `restore_check.ok == false`; a metric a rule names that is missing
  or not finite on either side (`not_measured`); a growth rule with `repeat` below
  `min_repeat_for_growth` on either side (`repeat_too_small`); a screenshot on one side only; an
  unmapped path, a not-run scenario, or an expected screenshot without a shot-diff row in the
  manifest; nothing compared. Fixtures cover `--shot-diffs` absent, empty and partly filled.
- **Rule formulas** (b = base, p = pr; both finite numbers or the rule's metric is `not_measured`):
  `increase_abs {max, field?}`: regress when p − b > max (field defaults to the metric name).
  `known_diff {min_abs, max_ratio}`: for each id in either map (missing id = 0), regress when
  p − b > min_abs and p > b × max_ratio. `list_new {max}`: size is the list length (duplicates
  count) or the number itself; regress when size(p) − size(b) > max; report up to 10 added entries
  by multiset difference. `increase_ratio_and_abs {min_abs, max_ratio}`: regress when p − b >
  min_abs and p > b × max_ratio (b = 0: only the absolute part can hold). `growth_diff {max}` on
  `growth_per_iter.<field>`: regress when p − b > max. `abs_max {max}`: shot-diff rows only,
  regress when ratio > max. Comparisons are strict (a delta equal to the limit is not a
  regression). Parity fixtures are pinned to SAKUJI `feat/feature-verify` at the revision recorded
  in the test file.
- **Preflight** `plumb-verify plan [--base <sha>] [--head <sha>] [--json]`: one outcome — `runnable`
  (exit 0: lookup, up, down, scenarios and thresholds all set and resolving), `invalid` (2, the
  contract does not parse), `unavailable` (3, no Python 3.11 `tomllib`; same meaning as
  `plumb-project`), `absent` (4, no contract or no `[verify]`, or an empty one), `partial` (5, some
  of the five keys missing), `unresolved` (6, a command or path does not resolve), `untrusted_head`
  (7, decision 10). The skill continues only on `runnable`.
- **Project commands** (from the base worktree, decision 9; each a command line):
  - `lookup --base <sha> --head <sha>` → stdout JSON `{features: [{id, distance, scenarios: [{id,
    repeat, auto_verify, draft, stateful, needs_ai}]}], unowned: [paths], skipped: […]}`
  - `up --ref <sha> --label base|pr [--role R]` → last stdout line JSON `{ok, url, project, …}`;
    progress on stderr. The labels are `base` and `pr` everywhere (rows, commands, output).
  - `down --project <name>` | `down --all`
  - `scenarios`: a path (the project's procedure for writing and running one scenario and producing
    observation rows) or a command
  - `thresholds`: a path to the thresholds file
SAKUJI's `select.mjs` and `verify-up.mjs` already have these shapes, including `--label pr`.

## Steps

1. `docs/verify-protocol.md` (above) and `docs/project-contract.md`: add `[verify] thresholds`.
   `scripts/plumb-project.py`: add `thresholds` to the verify keys; doctor's contract block checks a
   path key resolves to a file (as it checks commands).
2. `scripts/verify_compare.py` + `bin/plumb-verify` (dispatcher: `compare`, `plan`): the port.
3. `scripts/test-verify.py`, wired into `scripts/selftest.sh`: one fixture per outcome and per
   incomplete cause; every rule type at, below and above its threshold; legacy rows (`ok`, `error:
   "harness:…"`, `side: pr`); unknown rule → exit 2; malformed JSONL → exit 2 with the line number;
   `plan` on absent / set-and-resolving / invalid / unresolved contracts. A parity test runs the
   same fixture through SAKUJI's semantics as recorded expectations (no Node at test time).
4. `skills/verify/SKILL.md` (`plumb:verify`): an English description (skill files hold no CJK;
   the Japanese asks live in the trigger cases): load first, before reading the diff or running
   anything, whenever asked to check that a change works or did not regress — "verify this", "does
   it still work", "check it works in the app", "compare against base", a request to do a 動作確認
   is the same request — not for running unit tests, reviewing a diff, or a CI failure. `--dry-run`
   runs step 0 and returns without running any project command. Steps: 0 `plumb-verify plan
   --base … --head …`; `absent` → fallback (decision 8); any other non-`runnable` → stop with the
   outcome and its message. 1 base and head SHAs. 2 hand the run to the
   `verifier` agent (lookup, up both sides with the same flags/seed/roles, scenarios per the
   project's procedure, down in a finally). 3 `plumb-verify compare`. 4 report: result, compared
   scope, not compared and why, threshold status, findings; S1/S2 reproduced by a context-free
   subagent; never "pass" / "問題なし".
5. `agents/verifier.md` (no model) and `.codex/agents/plumb-verifier.toml`; the agent counts move
   deliberately: `check-harness.sh` (6→7 and 10→11) and the installation assertions in `selftest.sh`
   that expect 10 Codex agents (derive the expected count from the shipped `.codex/agents/*.toml`).
6. Root `SKILL.md` routing row; `docs/role-map.md` if roles are listed there.
7. `evals/verify/triggers.csv`: 6 asks (Japanese and English, 「動作確認して」 first) and 6 near
   misses ("テストを回して", "run the unit tests", "review this PR", "CI が落ちた", "この画面を作って",
   "fix this bug"). `scripts/trigger-eval.py` gains a `first_skill` measure (the target is the first
   skill invoked, not only one before the first other tool) with a scorer fixture that rejects a
   two-hop route; the release gate is first-skill recall 1.0 and 0 near misses routed.
8. Version 0.19.0, CHANGELOG, `docs/releases/v0.19.0.md`.
9. SAKUJI (separate draft PR after #1675 lands): `.plumb/project.toml` `[verify]` with lookup =
   `node scripts/feature-map/verify/select.mjs`, up = `node scripts/dev/verify-up.mjs`, down = `node
   scripts/dev/verify-down.mjs`, scenarios = `docs/agents/skills/feature-verify/SKILL.md`,
   thresholds = `scripts/feature-map/verify/thresholds.json`.
10. Acceptance F live runs on SAKUJI: a deliberately introduced regression found through the whole
    path (`regressed`), and a failed start reported `incomplete`. Acceptance G: `plumb-verify plan`
    and `/plumb:verify --dry-run` in a fresh cloud session find the contract and run no project command.

## Not in this lap

The browser measuring scripts, scenarios, fixtures, seeds and thresholds stay in SAKUJI (spec §F,
decision 4 of the spec). SAKUJI's `compare.mjs` stays until SAKUJI chooses to call `plumb-verify
compare`; parity tests keep the two from drifting meanwhile.
